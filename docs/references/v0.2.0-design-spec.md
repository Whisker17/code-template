# code-template v0.2.0 — 轻量实现与 Release 编排

状态：已获用户批准，由 WHI-1491 实施（§12.2 的五项提案一并获批）。实施记录与本文的对应关系见 `CHANGELOG.md` 的 v0.2.0 条目。本文自身不授予合并权限；授权以落地后的 `docs/GIT_WORKFLOW.md` 为准。

> 历史说明：以下正文保留设计阶段的原文。其中“本次只产出设计”等表述描述的是设计轮次，已由用户的实施授权取代。

来源：[Linear v0.2.0 项目更新](https://linear.app/whisker-personal/project/github-repo-template-3d0b49ffb1e0/activity#project-update-40212fb8)及后续设计讨论。

本文描述 **code-template 自身**的演进，单独存放于 `docs/references/`。`docs/DESIGN.md` 继续作为下游新项目的 PRD 模板，不能被模板自身的需求覆盖。下文的“必须”描述 v0.2 落地后的目标行为；实施前仍遵守现有 AGENTS.md 和 Git 工作流。

## 1. 问题与目标

当前模板将大量过程约束施加在每个 issue 上：强制 TDD、两条审查轴、三轮 review、escalation、ponytail 阶梯报告、重复的运行环境检查及完整陷阱列表。这些机制在 AGENTS.md、技能和运行时文档中重复描述，增加上下文消耗，也让规则更容易相互矛盾。

v0.2 的目标是：设计者把目标、约束、依赖和验收写清楚；实现模型自主完成有边界的任务；orchestrator 负责调度、集成和证据核对；独立 reviewer 在 release 集成后寻找实际缺陷。可靠性来自可验证的结果、隔离的审查上下文和明确的权限边界。

### 1.1 成功标准

- 普通版本 issue 不再强制执行 TDD、独立 review 或多轮审查，只要求满足验收及必要检查。
- 一个 release 可以按依赖关系完成实现、集成、整体审查和有界修复，换一个 orchestrator 仍能继续。
- 模型名称和 effort 的运行时映射只有一个配置来源；模型升级不需要修改技能正文。
- 默认保留 8 个核心技能，移除强制阶梯报告及完整历史陷阱注入。
- AGENTS.md 仅承载常用项目事实、关键约束和按需入口；不复制完整 Git、Linear、编排流程。
- 自动集成不等于允许发布；高风险修改及版本晋级仍有明确的人审边界。
- 能从提交、PR、Linear 记录和验证产物重建进度，而非依赖聊天中的“已经完成”。

### 1.2 非目标

- 不构建新的调度服务、数据库、消息队列、通用 DAG 引擎或 Web 控制台。
- 不自动部署，不改变 tag 作为部署来源的规则。
- 不改变项目技术栈，不引入新的编程语言或依赖框架。
- 不把模型的一般编程能力改写成长篇操作教程。
- 不自动同步所有下游仓库；继续由下游主动采用模板更新。
- 本次只产出设计；不创建实现 tickets、不修改 Linear 状态、不执行实现或发布。

## 2. 关键决策

| 主题 | v0.2 决策 | 原因 |
| --- | --- | --- |
| 实现方式 | implementer 自主实现，遵循 ponytail，按验收验证 | 避免为所有任务强制同一种开发过程 |
| 审查位置 | 普通版本工作在 release 集成后统一独立审查 | 能看到跨 issue 问题，减少重复上下文 |
| 修复版本 | 发布前的 review 修复属于原 Release | Release 表示交付版本，不能兼任审查轮次 |
| 审查上限 | 最多 3 次完整 release review，最多 2 个自动修复批次 | 每个自动修复批次之后都保留复审机会 |
| 调度 | 依赖已满足且不存在模块／共享契约冲突的任务才并行 | Linear 没有 blocks 不代表修改互不影响 |
| Git | 保留现有基线解析、worktree、PR、合并策略和 fan-out | 降低迁移范围，维持可追溯性 |
| 角色 | ORCHESTRATOR、IMPLEMENTER、REVIEWER | 去除默认 ESCALATOR 和 EXPLORER 角色 |
| 难度 | issue 标记 medium 或 high，映射到实现 effort | 将设计阶段的信息用于实际调度 |
| 测试 | 优先验证外部行为；采用能发现相关失败的最小检查 | 不强制 TDD，也不强制只能使用 E2E |
| 指令入口 | AGENTS.md 单一入口，删除模板中的 CLAUDE.md 链接 | 目标 Claude Code 已支持原生加载，兼容条件见 §9 |

最重要的前提：版本集成分支允许暂存尚未完成 release review 的工作。若直接进入生产或要求始终可发布，则必须使用 §6 的合并前审查路径，不能套用普通版本 issue 的快速集成规则。

## 3. 术语与完成语义

| 术语 | 定义 |
| --- | --- |
| Release | 一组最终随同一版本发布的修改；与 tracker Release、Git tag、GitHub Release 对齐 |
| 版本集成分支 | 承接该版本 issue PR 的长生命周期分支；尚未通过 release review 时不能视为可发布 |
| 实现完成 | 实现者已打开 PR，提交验收证据并完成 handoff；issue 通常处于 In Review |
| issue Done | PR 已合入解析出的基线，并完成规定的清理和 fan-out；不代表已发布 |
| release review | 独立 reviewer 对固定版本快照进行需求、正确性、集成和复杂度审查 |
| 修复批次 | 某次 review 产生的一组实际缺陷修复；仍属于原 Release，不生成新版本号 |
| release ready | 当前确切提交通过完整验收和独立审查，且没有阻断项；等待晋级／发布的人审 |
| released | 已按现有发布流程交付，并完成 tracker、tag、GitHub Release 的一致性记录 |

0.2.0 发布前发现的问题继续进入 0.2.0。0.2.0 发布后需要补丁时，再按照发布／hotfix 工作流创建相应版本。本文不改变现有 hotfix 的版本编号约定。

## 4. 角色与模型配置

### 4.1 职责

| 角色 | 职责 | 不承担 |
| --- | --- | --- |
| ORCHESTRATOR | 读取完整 issue 集、检查依赖、分派任务、核对证据、串行合并、维护进度、安排审查和修复 | 不亲自实现功能，也不代替 reviewer 宣布审查通过 |
| IMPLEMENTER | 在独立 worktree 中实现一个 issue，运行相关验证，打开 PR，提交 handoff | 不自行扩展 scope、不自行创建下一发布版本 |
| REVIEWER | 在独立上下文中进行 adversarial review，提供可验证的发现和结论 | 不直接修改被审查代码，不用大量风格建议充当缺陷 |

普通探索由承担任务的模型直接完成，不再需要一个必备的 EXPLORER。取消自动 ESCALATOR；超出审查预算的未决问题交给人处理。

### 4.2 单一配置来源

沿用 `config/agent-roles.conf` 和 `scripts/agent-dispatch.sh`，不新建第二套模型注册表。

每个角色配置运行时、准确模型 ID，以及该运行时使用 medium / high effort 的映射。公共调度接口为：

```text
scripts/agent-dispatch.sh <ROLE> <prompt-file|-> --effort <medium|high>
scripts/agent-dispatch.sh --probe [ROLE ...]
```

- 模型 ID 只存放在角色配置中，不能同时写死在命令模板和技能里。
- `--effort` 是模板的语义参数，由适配器转换成对应运行时的参数；不能原样透传后假定两家 CLI 含义相同。
- 原生 subagent 调度与 subprocess 调度必须遵循同一模型、effort、工作目录和输出约定。
- 配置不含密钥；认证使用运行时既有登录方式或环境变量。
- 未知角色、未知 effort、缺少模型或不支持 effort 时明确失败，不能静默换模型或降低 effort。
- 启动 release 时，为本次会使用的角色执行一次真实轻量调用；同一配置不在每个 issue 前重复。配置改变或出现认证／调用错误时重新检查。
- `--probe` 只检查静态配置和命令可达性；不得将它表述为认证及真实调用成功。

用户希望的模型组合为 implementer `opus-5-5`、reviewer `astra-6`。这是选型意图，尚未证明它们就是本机 provider 接受的精确 ID。SETUP 必须从目标运行时核实 ID 和 effort 支持，并以一次真实调用作为配置完成标准。不能把未验证的名称写成已可运行的默认值。

ORCHESTRATOR 和 release REVIEWER 使用 high；IMPLEMENTER 按 issue 难度使用 medium / high。角色配置规定目标 orchestrator 模型，若当前会话不匹配，应启动匹配的会话并 handoff；不能声称当前会话已被配置文件切换模型。

### 4.3 issue 难度

在 issue template 中新增必填章节：

```markdown
## Execution
- Complexity: medium | high
- Reason: 一句话解释难点
- Expected scope: 预期修改的文件、模块及共享契约
```

实际 Linear issue 按现有规则使用英文。上面的 `medium | high` 表示两个允许值，发布 ticket 时必须选定一个。

| 难度 | 适用情况 |
| --- | --- |
| medium | 局部、模式明确、验收直接、无明显跨模块推理难点 |
| high | 跨模块行为、并发或恢复逻辑、数据一致性、安全边界、复杂迁移或难定位的根因 |

难度与优先级、工作量、人审风险等级分开。修改很小也可能 high；大量机械改动不一定 high。设计者在 to-tickets 时给出初值，orchestrator 可根据实际证据升级为 high 并记录原因；不静默降级。缺失难度先补全，不默认猜测。

## 5. Release 编排

### 5.1 输入与预检

输入为明确的 Linear 项目和 Release；不能只按相似标题或 milestone 猜测。

orchestrator 必须读取所有分页，包括 issue 状态、Release、原生 blocks / blocked-by、难度、验收和预期修改范围，构建当前任务集合。原生关系是依赖事实来源；正文是可读镜像，二者不一致时先修正。

预检包括：

1. 按现有规则核对版本前缀与 Release，解析 Git 基线；版本分支不存在时报告阻塞，不随手创建。
2. 检查外部依赖、循环依赖、无法满足的验收和缺失难度。
3. 识别高风险路径，以及会修改同一模块或共享接口的任务。
4. 检查 GitHub、Linear 和所需角色可用；核对项目现有验证命令。
5. 记录当前计划 issue 集、固定的审查基准提交 B，以及集成分支。

B 是该版本继承的、已验证的起点提交，并在本次编排中保持不变。接管已有实现的 release 时，必须通过既有记录核实起点，不能把当前 HEAD 当起点而漏掉已完成工作。无法确认时先恢复审查范围证据。

被取消的 blocker 不自动算满足：依赖其产物的 issue 必须有明确的替代方案或关系修正。外部 blocker 未完成时只阻塞依赖它的任务，其余独立任务可继续。

### 5.2 调度与集成

```text
Linear Release / issues ──读取──> ORCHESTRATOR
                                  │
                     分派 issue   │   分派固定快照
                         ┌────────┴────────┐
                         ▼                 ▼
                    IMPLEMENTER        REVIEWER
                         │                 │
                    worktree / PR       findings
                         │                 │
                         └────handoff──────┘
                                  │
                         核对、合并、更新 Linear
                                  │
                           新任务或修复批次
```

- 只有所有实际依赖已满足的 issue 才可启动；依赖前序代码时，前序 PR 必须已合并。
- 相同模块、共享 schema、公共接口或共享生成文件有冲突风险时串行；不以“Git 能自动合并”作为可并行证明。
- 独立任务使用多个 subagent，每个 issue 一个 worktree 和 PR。并发上限使用运行时已有设置；无法确认容量时先串行，不另建调度器配置系统。
- implementer 读取 issue、相关 spec 和必要流程，完成 ponytail 实现、相关检查、PR 及 handoff。
- orchestrator 核对 PR scope、基线、提交和检查结果，串行处理合并、清理与状态更新，避免多个 subagent 同时操作主克隆。
- 基线前进导致冲突或语义影响时，implementer 更新分支并重跑受影响检查。不能复用旧 HEAD 的通过结论。
- 实现中发现 scope 冲突时，暂停有冲突的任务并重新排序；不自动扩大 issue 或让两个 agent 同时覆盖同一成果。

### 5.3 issue 状态所有权

orchestrate 模式由 orchestrator 统一负责 tracker 状态；implementer 返回事实和 PR。在独立 implement 模式，当前 agent 承担同样责任。

| 事件 | Linear 状态 |
| --- | --- |
| 已领取，开始实现 | In Progress |
| PR 已打开 | In Review |
| PR 已合并且规定清理完成 | Done |
| 等待人审或验证失败 | 保持 In Review，并记录阻塞原因 |

若 PR 创建到通知 orchestrator 存在时间差，orchestrator 在收到事件后立即同步。恢复会话时优先核对真实 PR 状态，修复漂移，不重复创建或合并。

### 5.4 交接与持久化

沿用 handoff，内容只包括：

- issue、spec、PR、分支、worktree 链接／路径及解析出的 base。
- 当前 commit SHA、实现结果、验收命令、结果和产物位置。
- 未决问题、失败或未运行的检查，以及下一步。
- 对依赖任务的影响；有结论修正时附证据。
- 实际使用的角色、模型和 effort。

临时 handoff 文件可以沿用操作系统临时目录；它不能成为恢复任务的唯一来源。关键结果进入 PR／issue，release 级基准 B、当前轮次、已审查 SHA、发现及修复映射保存在项目下的一份 Linear 编排文档中，并从相关任务引用。文档名称为 `Release X.Y.Z — orchestration`；复用同一文档，不为每轮新建一份。

聊天记录、进程仍在运行、自述“已完成”都不能替代提交和验证证据。无需每次重新运行全部检查；只有证据缺失、HEAD 变化或出现具体疑点时才重跑。

## 6. 合并授权与 Git 保留边界

### 6.1 目标授权表

以下替代当前“必须三轮 review 才能自合并”的规则，需在正式实施时同步修改所有规则载体。

| 工作类型 | 合并前要求 | 自动合并 |
| --- | --- | --- |
| 普通 issue → 已存在的版本集成分支 | 验收及必要检查通过，PR 可合并，orchestrator 核对证据 | 可以；独立审查推迟到 release 集成后 |
| 首次发布前的 bootstrap issue → dev | 同上；dev 此时明确承担首次版本集成用途 | 可以；首次发布仍须完整 release review |
| repo-wide governance → dev | 必要检查及一次独立 PR review 通过 | 可以；随后按现有规则 fan-out |
| 独立 implement、无 release 审查编排接管 | 必要检查及一次独立 PR review 通过 | 非人审例外时可以，不能承诺一个无人负责的未来 review |
| 命中项目高风险路径 | 必要检查；等待人审 | 不可以 |
| hotfix → main | 必要检查、独立审查及人审 | 不可以；生产入口统一由人批准 |
| 完成的版本集成分支 → dev | 当前 SHA 的完整验收和 release review 通过；人审 | 不可以 |
| 临时 release 分支 → main | 按现有发布流程，人审 | 不可以 |

治理修改直接影响其他活跃分支，因此保留一次合并前独立 review。这里取消固定多轮数；修改了被审查内容后，仍必须核对最终提交，不能将旧审查套到新提交。

reviewer 不可用时，可继续普通 issue 的实现和隔离分支内集成，但 release 必须停在 blocked，不能晋级。需要合并前独立 review 的路径保持 In Review。

### 6.2 不变的 Git 规则

保留：基线三分类、版本前缀与 tracker Release 双信号、worktree 隔离、显式 PR base、按 lane 选择 squash 或 merge commit、dev 前进后的 fan-out、hotfix backmerge、tag 部署以及主分支保护。

治理 issue 继续不带版本前缀、不绑定 Release。release 如依赖治理变更，由普通版本任务的原生 blocked-by 关联这些治理 issue；不能为了让 release 列表看起来完整，给治理 issue 伪造 Release。

本次模板 v0.2 的落地也遵循上述拆分：修改 AGENTS、skills、runtime 等 carve-out 文件的工作走治理 lane；若修改 SETUP、锁文件或其他不在 carve-out 内的文件，则按现有分类单独处理，不能把混合修改强行算治理。

### 6.3 与当前规则的明确冲突

当前 AGENTS.md、`docs/GIT_WORKFLOW.md`、`docs/agents/runtime.md`、implement 和 orchestrate 都把三轮 review 当作自合并前提；本设计将其替换为上表。当前 hotfix 规则允许满足旧审查条件的非高风险工作自合并，本设计收紧为所有生产入口由人批准。

这些是待实施的政策变更，不是当前会话的临时豁免。必须在一个一致的治理变更中更新全部权威规则及 README／PR 模板说明，然后 fan-out；旧版本 agent 不得仅凭本文跳过现行门槛。

## 7. Release 审查与修复循环

### 7.1 审查输入与职责

所有计划中的 issue 均已集成、外部依赖满足、完整验收通过后，冻结候选提交 H，交给一个全新 REVIEWER 上下文。

输入必须包含：固定基准 B、候选 H、`B..H` 的实际树差异、全部 issue 的验收、spec、检查产物，以及已知发现及修复记录。reviewer 可以读取完整 H 树，核对交互行为；不能只审最后一个 PR。第一轮覆盖完整版本，后续轮次仍对完整候选版本负责，并重点复核修复及其影响。

审查覆盖：

- 是否满足 spec 和每个 issue 的验收。
- 错误处理、边界条件、状态恢复、安全及数据完整性。
- 跨 issue 的接口和行为是否一致。
- 验证是否真的证明了需求，是否存在空差异或无效测试。
- ponytail 原则：已有能力是否被重复实现，是否引入无必要的依赖和抽象。

一个 reviewer 在同一轮覆盖这些方面；不再强制拆成 Standards / Spec 两个 reviewer。reviewer 必须与实现者上下文隔离，优先跨厂商；不宣称存在可自动判定“模型能力至少相等”的可靠排名。

### 7.2 发现格式与处理

每项发现包含：稳定编号（如 R1-F1）、严重度、文件／行为定位、触发条件、证据或可复现方式、违反的需求及最小修复建议。

- **阻断项**：实际错误、验收缺失、关键验证缺失、安全／数据问题，以及确实违反明确复杂度约束的问题。
- **建议项**：不影响验收的风格偏好、可选整理和未来增强，不阻断 release，不自动生成实现任务。
- 无法复现或证据不足的结论标记“待核实”，不能当作已证明缺陷；涉及关键验收的不确定性在解决前仍阻断通过。

orchestrator 对发现去重并核对 scope；不能仅凭实现者反驳关闭发现。存在实质分歧时交由 reviewer 复核；无法解决则转人判断。

接受的阻断项创建为同 Release 的修复 issue，遵循标准 issue template 和 medium / high 难度。一个独立根因对应一个 issue；多个发现共享同一根因时可合并。issue 正文带 `Review round`、发现编号、候选 SHA 和原始 review 证据，编排文档维护映射。创建前检索已有映射，恢复或重试不得重复建单。

修复同样经过 implement → PR → handoff → 核对集成。原 issue 已 Done 的保持 Done，用新修复 issue 记录新增工作。

### 7.3 三轮上限

| 阶段 | 行为 |
| --- | --- |
| Review 1 | 审查完整候选 H1；无阻断则 ready，否则生成修复批次 1 |
| 修复批次 1 | 同 Release 内实现并集成，验证得到 H2 |
| Review 2 | 审查 H2，复核原发现和回归；仍有阻断则生成修复批次 2 |
| 修复批次 2 | 同 Release 内实现并集成，验证得到 H3 |
| Review 3 | 审查 H3；通过则 ready；仍有阻断则 blocked，移交人处理 |

预算按一次实际完成的候选快照审查计数；认证失败或没有输出不算通过，也不算完整审查。技术失败记录原因，不自动无限重试。第三轮的未决阻断项仍要建单或更新已有 issue，但不自动启动第四轮或一个无复审的修复批次。

“通过”表示 **无未解决阻断项且当前 SHA 的验收有效**，不要求 reviewer 完全没有任何建议。范围外建议按现有 deferred 约定保留理由和引用；不能把阻断项改名为建议来让版本通过。

### 7.4 候选变化与发布

review 期间不向候选分支合并普通新功能。若必要 fan-out 或其他授权变更推进了 HEAD，旧结论仅适用于旧 SHA，当前候选必须重新验证与审查；已用轮次不归零。轮次耗尽则人审接管。

release ready 的证据绑定 H。集成分支合入 dev 时若产生新的冲突解决或代码变化，必须验证最终合并结果并审查相关变化；原 H 的通过不能覆盖新代码。随后按现有临时 release cut、main 人审、tag 和发布流程执行。

## 8. 验证策略

### 8.1 项目实现过程

- 验收目标先于实现确定，但不要求先写所有测试代码。
- 开发中运行受影响的测试、lint／类型检查及必要局部 E2E，不反复运行完整 E2E。
- 有分支、解析、并发、资金或安全逻辑的改动，留下能发现实际失败的可运行检查；避免只复刻实现细节的断言。
- E2E 适合用户流程；模块级测试适合难以从 E2E 稳定触发的边界与失败模式。两者都允许。
- 在 release 候选集成完成时执行完整项目验收，包括项目已有的完整 E2E。模板不强迫没有 E2E 的项目引入浏览器框架。
- 修复批次完成后，对新候选再次运行完整验收；不对未改变的候选无理由重复。
- 产物包含提交 SHA、命令、结果、必要环境信息及报告／日志／截图等适当证据；不能只给“测试通过”一句话。

### 8.2 模板自身验收场景

沿用现有测试工具和临时 Git 仓库；调度逻辑能用假的 CLI、假的 tracker 响应验证时不消耗模型调用。仅用少量真实调用确认配置可达性。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 两个独立 issue 加一个依赖 issue | 前两项可并行；依赖项等待前序合并 |
| 无 blocks 但共享模块／接口 | 串行或先修正任务边界 |
| 分页、外部 blocker、取消的 blocker | 不漏 issue，不把未满足依赖当作可执行 |
| 循环依赖或版本信号不一致 | 明确阻塞，不猜 base、不创建分支 |
| medium / high 调度 | 实际调用的模型与 effort 匹配配置 |
| 未知角色／effort、认证失败 | 明确失败，无静默模型替换或降级 |
| PR 未合并但 agent 报完成 | 保持 In Review，不标 Done |
| 合并后 tracker 写入失败再恢复 | 对账后补状态，不重复合并或建单 |
| 高风险、governance、hotfix、bootstrap | 严格走 §6 对应的授权路径 |
| release review 出现缺陷 | 修复 issue 留在原 Release，映射可追溯 |
| 第三轮仍有阻断 | blocked，保留问题，无第四轮自动循环 |
| review 空差异但 release 声称有新实现 | 核对范围，不当作通过 |
| review 后 HEAD 改变 | 旧证据不能授权新候选晋级 |
| 删除临时 handoff 后恢复 | 仍能从 GitHub、Linear 和编排文档接续 |
| Claude Code 指令加载 | 新会话实际加载 AGENTS.md，能列出其路径 |

Markdown 和技能改动本身不需要形式化单测；检查断链、残留强制旧流程、删除后引用，以及实际场景演练。对新增／修改的 dispatch 参数解析和失败处理保留可运行测试。

## 9. 指令与技能精简

### 9.1 AGENTS.md

保留项目描述、当前状态、真实 build/test/lint 命令、关键安全约束、最短 Git／tracker 门槛及按需链接。Git 细节以 GIT_WORKFLOW 为准，角色配置以 runtime 为准，issue 结构以 issue-template 为准。

不复制完整分支生命周期、每一步 shell 命令、历史故障长篇说明或模型本身能从代码获得的信息。相关细节仍在专门文档中，需要时读取；不使用会在启动时展开全部文档的导入方式伪装精简。

体积目标是显著低于当前版本，并以官方建议的 200 行以内作为上限参考；不能为了数字删除关键权限边界。验收时记录 AGENTS.md 和默认技能描述的前后大小，不能用未经测量的 token 节省比例作结论。

### 9.2 CLAUDE.md 兼容条件

Claude Code 当前官方文档已支持原生 AGENTS.md：支持从 v2.1.277 开始；更早的一些运行环境差异在 v2.1.281 修复。因此模板采用 v2.1.281 或更新版本作为此能力的支持基线。

默认模式下，工作目录或祖先目录中的 CLAUDE.md、`.claude/CLAUDE.md`、CLAUDE.local.md 可能使 AGENTS.md 不被加载。SETUP 必须提示检查该情况，并通过 `/memory` 等实际加载记录验证。可由用户设置 `claude-md-and-agents-md`；不能假定仓库内设置会覆盖用户／管理设置。

模板删除根 CLAUDE.md 链接，不自动修改用户全局配置。旧客户端的项目可自行保留兼容导入，但这不是 v0.2 默认模板支持范围。

### 9.3 默认技能清单

| 保留技能 | 边界 |
| --- | --- |
| grill-me | 通过讨论澄清目标、约束与验收，避免重新询问已确定事项 |
| to-spec | 从讨论产出项目 spec；默认写 docs/DESIGN.md，模板自身设计使用独立文档；发布行为遵循用户指令 |
| to-tickets | 使用仓库 issue template，填写难度和范围，创建 Linear 原生依赖 |
| implement | 单 issue 实现、必要验证、PR 和 handoff；不内置固定审查循环 |
| orchestrate | release 调度、集成核对、整体 review 和有界修复 |
| code-review | 独立 adversarial review；支持固定 PR 范围和 release 快照 |
| handoff | 简短交接，引用证据，持久化关键状态 |
| ponytail | 最少必要实现；不降低验收、错误处理、安全和可访问性要求 |

其余当前随模板分发的技能从默认集合删除，包括 tdd、两个重复的 grilling 入口、ask-matt 及通用研究／探索／教学技能。需要它们的项目可自行安装，模板不维护第二套“可选技能包”机制。删除前将仍被保留技能依赖的必要契约归入对应权威文档，清除悬空引用。

移除 ponytail 强制阶梯报告和独立 shrink-pass 报告。新依赖和重要抽象仍须在 PR 中说明必要性，但不为没有新增抽象的修改制造空表格。

`docs/TRAPS.md` 中可复用的约束归入相关文档；项目专属历史记录可保留为按需参考，orchestrator 不再默认将全部内容复制给每个实现者。

### 9.4 Linear 与设计链路

- to-spec 不固定要求长篇 user stories，也不强制为每份草案创建 ready-for-agent issue。
- to-tickets 必须读取 `docs/agents/issue-template.md`，不能使用技能自己的竞争模板；保留明确路径、验收、依赖、难度和 scope。
- ticket 的 title prefix 与 Release 必须一致；Milestone 不参与版本路由。
- MCP 优先，API fallback 沿用现有 ladder；无可用 tracker 时报告阻塞，不建立影子 tracker。
- Release 获取、issue 绑定、原生依赖和文档操作必须通过目标 workspace 的实际工具／API 验证，不凭字段名猜测。当前已验证能读取来源项目更新；本次未验证所有写入接口，也未尝试写入。

## 10. 落地顺序与迁移

预计涉及超过 8 个文件，且包含技能删减；按下列可独立完成的变更组织，具体 tickets 在设计确认后拆分。

1. **角色调度基础**：让 IMPLEMENTER 可调度，统一模型与 effort 配置、真实预检和 handoff 数据；旧流程仍可使用原角色，新增能力先向后兼容。完成相关参数／错误路径测试。
2. **执行与审查政策切换**：在一个一致的治理变更中更新 implement、orchestrate、code-review、ponytail、runtime、Git、AGENTS、issue template、tracker 文档、PR 模板和 README。新闭环完整可用后，取消旧的多轮授权、ESCALATOR 和默认 EXPLORER。不能先删 review gate、以后再补 release gate。
3. **默认分发收口**：删除非核心技能及 CLAUDE.md，清理 lock、SETUP、索引和交叉引用；SETUP 采用新角色配置并验证 AGENTS 加载。此阶段之前保留的旧辅助技能不再参与默认主流程。

每项仍按现有 Git 分类拆成适当 issue／PR；属于不同 lane 的变更用原生依赖排序。阶段 2 是互相依赖的政策切换，不假装可以拆成各自独立的半套授权流程。

治理问题的 fan-out 必须在同一会话完成，但进行中的旧任务应先完成或暂停并交接，再切换执行契约。编排文档记录使用 v0.1 或 v0.2 的流程版本，防止任务按旧规则启动、按新规则误判完成。

回滚使用正常 revert PR 恢复旧技能、配置与授权规则，保留已经创建的 issue、评论和 review 记录；暂停新调度，对照真实 PR／提交状态恢复。不得以重置分支或删除审查历史进行回滚。

## 11. 已拒绝方案

| 方案 | 拒绝原因 |
| --- | --- |
| 每个 issue 强制三轮 review 加 escalation | 重复加载上下文，且无法代替整体集成审查 |
| 禁止实现后补单测 | 限制必要回归验证，与结果导向无关 |
| 只允许 E2E | 某些边界、并发和失败路径难以稳定覆盖，增加成本 |
| 每轮 review 创建下一个 patch Release | 把审查批次混同于交付版本，破坏 Git 路由语义 |
| 只根据 Linear blocks 并行 | 漏掉共享模块和接口冲突 |
| 无需验证直接相信 handoff | 任务报告可能滞后、遗漏或引用旧 SHA |
| 审查三轮后再自动修一次就结束 | 最终修复没有独立复审，不能视为通过 |
| 为所有 review 建议自动建单 | 风格意见容易演变成无限 scope 和成本 |
| 将全部规则压缩进 AGENTS.md | 仍然每次加载，且继续重复维护 |
| 新建一个编排服务或持久化数据库 | Git、Linear 和现有运行时已能承载所需状态 |

## 12. 风险、待确认提案与证据边界

### 12.1 设计风险

- **审查发现较晚**：release review 才暴露跨 issue 问题。通过清晰接口、局部验证和模块冲突串行缓解；不能假定晚审查适合直接入生产的工作。
- **规则切换期间混用**：用一致的治理变更、fan-out 和流程版本记录处理，避免同一 release 同时执行两套授权。
- **人工门槛阻塞自动完成**：高风险 issue 的依赖链可等待人审；orchestrator 继续独立工作，但不能称 release 已全部完成。
- **长时间运行中断**：通过 tracker／Git 状态和单份编排文档恢复；平台不可达时暂停需要该事实或写入的步骤，不能推断成功。
- **说明变短但隐藏重复读取**：同时检查入口大小及实际主流程加载的材料，不只缩短一个文件。

### 12.2 本草案新增的具体提案

前文已讨论并获得方向性认可：同 Release 修复、取消强制 TDD、release 级审查、并行冲突检查、复用角色配置。

本稿进一步作出的以下选择尚属设计建议，供下一轮讨论：

1. 三轮解释为最多三次完整 review 和两个自动修复批次。
2. 默认技能缩减为 §9.3 的八个，其他技能不随模板分发。
3. governance 和独立 implement 保留一次合并前独立 review。
4. 所有 hotfix → main 都需要人审，统一生产入口边界。
5. 以一份 Linear 编排文档持久化 release 状态；临时 handoff 只作传递。

这些选择不会因草案写入文件而自动生效。

### 12.3 实施前验证责任

实施者在角色配置变更中验证准确模型 ID、effort 支持和 CLI 调用；在 Linear 适配变更中验证目标 workspace 的读写及 Release 绑定；在 SETUP 变更中验证 AGENTS.md 实际加载。若验证失败，调整配置或报告明确阻塞，不能把假设作为已测试能力。

这些是部署环境的验收条件，不需要为本次设计编造可用的模型 ID、版本分支、Linear 字段或认证信息。
